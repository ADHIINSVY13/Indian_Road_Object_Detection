# Code walkthrough

What every part of the repository does, why it exists, and what to say if someone points at it and asks
"what does this do?". Numbers quoted here come from `results/` and the reports in `docs/`.

## 1. The whole pipeline in one picture

```
raw IDD download (VOC XML + JPEG)
      │  scripts/inspect_annotations.py   look at the real files first
      ▼
  src/preprocessing/voc.py ──► convert.py ──► validate.py        scripts/prepare_dataset.py
      parse XML       convert to YOLO txt    check the result
      ▼
 data/yolo  (images/ + labels/ + idd.yaml)        scripts/analyze_dataset.py ─► results/eda/
      ▼
 scripts/train_yolo.py  (Colab T4)  ──► models/best.pt, results/results.csv
      ▼
 scripts/evaluate.py  ──► results/eval_finetuned.json     (IDD-finetuned model)
 scripts/evaluate.py --coco-baseline ──► results/eval_coco_baseline.json   (COCO model)
      ▼
 scripts/compare_evals.py ──► results/comparison.json + results_compare.png
 scripts/qualitative.py   ──► results/qualitative/  (side-by-side pictures)
```

The experiment: same architecture (YOLO11n), once with COCO weights as they are, once fine-tuned on IDD,
both scored on the same IDD val split. The question is how much fine-tuning helps India-specific classes
compared with common ones.

## 2. Folder map

| Folder | Role |
|---|---|
| `configs/` | the only places settings live: `dataset.yaml` (paths, image size), `class_mapping.yaml` (15 classes and their COCO equivalents) |
| `src/` | reusable library code, imported by the scripts and by the tests |
| `scripts/` | command-line entry points, one per pipeline step |
| `tests/` | automatic checks on tiny synthetic data |
| `results/` | everything generated by a run (numbers, plots, galleries) |
| `docs/` | written reports |
| `notebooks/` | the Colab training notebook and the exploration notebook |

Rule behind the layout: logic goes in `src/` (so it can be tested), scripts only parse arguments and call it.

## 3. File by file

### Configuration
- **`configs/class_mapping.yaml`** — the 15 IDD classes in order (the order *is* the YOLO class id), each
  tagged `common`, `ambiguous` or `india_specific`, with the COCO class ids it corresponds to.
  *Why it matters:* the whole comparison depends on it. A COCO model cannot name `autorickshaw`, so that class is
  `india_specific` and the baseline is reported N/A, never 0.
- **`configs/dataset.yaml`** — where the raw data and the converted dataset live, the resize limit
  (`max_side: 640`) and the minimum box size.
- **`src/data/config.py`** — `load_yaml`, `resolve` (turns a repo-relative path into an absolute one) and
  `load_classes` (reads the mapping into `ClassInfo` objects). `normalize_label` lower-cases names and
  replaces `_` with spaces so `Traffic_Light` and `traffic light` are the same class.

### Step 1: inspect the real data
- **`scripts/inspect_annotations.py` + `src/preprocessing/inspect_annotations.py`** — before writing any
  converter, look at the actual download: file types, the first few raw annotation files, every class name
  that really occurs, box coordinate ranges, which split files exist. *Why:* converters written from
  assumptions about a format silently produce wrong labels. This step is where the odd XML tag order and the
  missing test labels were found.

### Step 2: convert and validate
- **`src/preprocessing/voc.py`** — `parse_voc_xml` reads one Pascal-VOC XML file. It reads each box
  coordinate by tag name (`xmin`, `ymin`, ...), so IDD's unusual order of those tags does not matter. It never raises
  on a bad file: it records the problem in `problems` and carries on.
- **`src/preprocessing/convert.py`** — `convert_dataset` turns each image + XML into a YOLO sample:
  a `.jpg` plus a `.txt` with one line per box, `class cx cy w h`, all normalised to 0-1.
  Per box it: rejects unknown class names, drops boxes with zero/negative size, clips boxes that stick out of the image, and flags tiny
  boxes. Per image it checks that the XML size matches the real image and skips the image if the *aspect ratio*
  disagrees (the boxes could not be trusted). Every drop is written to `conversion_issues.csv` with a reason code.
  `resize_image` shrinks the longer side to 640 px (LANCZOS filter); labels are normalised, so they stay correct after resizing.
  `flat_name` turns `seq/frame` into `seq__frame` so each file name is unique in one folder.
  *Why 640 px:* the full release is far larger than Colab and Drive comfortably handle; measured result
  41,794 images → 2.48 GB.
- **`src/preprocessing/validate.py`** — `box_issues` / `clip_box` are the per-box rules;
  `validate_yolo_dataset` re-reads the *converted* files and checks line format, class id range, coordinate range,
  duplicate lines and image/label pairing. *Why a second check:* it verifies the output, not just the input,
  so a converter bug cannot pass unnoticed. Result on the real data: 0 errors, 5 duplicate-box warnings.
- **`scripts/prepare_dataset.py`** — runs conversion then validation, prints issue counts by code, and exits non-zero if validation finds errors.

### Step 3: understand the data
- **`scripts/analyze_dataset.py` + `src/visualization/eda.py`** — counts boxes per class and split, box-size
  distribution, objects per image, share of small objects. Everything is computed from the label files
  (nothing typed in by hand). `results/eda/` holds the figures; `docs/dataset_report.md` interprets them.
  *Key finding:* strong class imbalance (e.g. motorcycle 78,119 train boxes vs trailer 11).

### Step 4: train
- **`scripts/train_yolo.py`** — fine-tunes `yolo11n.pt` (COCO-pretrained) on the converted IDD data using Ultralytics.
  Every hyper-parameter is a command-line argument and is recorded, so a number can be traced to a command.
  Details worth knowing: it rewrites `idd.yaml` on every run so the same checkout works on Colab and a laptop;
  `--resume` continues from `last.pt` (needed because Colab sessions end); `--seed` and `--patience` (early stopping)
  are exposed; augmentation is left at Ultralytics defaults on purpose, because the question is "does IDD
  fine-tuning help", not "what is the best augmentation".
- **`notebooks/02_train_colab.ipynb`** (generated by `scripts/make_train_notebook.py`) — the Colab recipe:
  mount Drive, unpack the dataset to fast local disk, clone the repo, run `train_yolo.py` with the run folder on Drive so a disconnect does not lose checkpoints.
- **`scripts/plot_training_curve.py`** — plots the per-epoch training curve from `results/results.csv` (the file the trainer wrote, not the console log) into `results/training_curve.png`.
  *Fact:* 23 of the planned 30 epochs ran (Colab free GPU quota ended); mAP50-95 rose from 0.134 to 0.202.

### Step 5: evaluate
- **`scripts/evaluate.py`** — scores a model on the val split and writes `results/eval_<tag>.json`.
  - `build_eval_dir` makes a temporary copy of the val set (images hard-linked, so no disk cost) whose labels are
    rewritten into the evaluated model's class space.
  - `--coco-baseline` mode: a COCO model predicts 80 COCO classes, so IDD ground truth is first translated to COCO ids
    and **only for classes with exactly one direct COCO match** (person, car, truck, bus, motorcycle, bicycle, traffic light, train).
    `rider`, `traffic sign` and `animal` are ambiguous and left out; `india_specific` classes are N/A.
  - `ap_by_class_id` / `compact_by_class_id` — *the bug that was fixed:* Ultralytics returns per-class AP
    (`box.maps`) indexed by class id, but precision/recall/AP50 (`box.p`, `box.r`, `box.ap50`) as a compact list for
    only the classes that have ground truth. Pairing them by position shifted every value whenever a class was
    absent (always the case for 80-class COCO). The first baseline report therefore showed wrong
    per-class numbers; this was caught, fixed, a regression test was added, and the baseline was re-run.
  - Output includes per-class `precision`, `recall`, `ap50`, `ap50_95` (`per_class_detail`) and per-group mean AP.
- **`scripts/compare_evals.py`** — joins the two JSON files into per-class deltas and per-group means, and draws
  `results/results_compare.png`. Classes the baseline cannot score stay `None` and are left out of its group mean
  rather than counted as 0, which would unfairly blame the model for a vocabulary gap.
- **`scripts/qualitative.py` + `src/visualization/qualitative.py`** — draws ground truth | COCO baseline | fine-tuned
  on the same image. Two galleries: a seeded random sample (so nothing is cherry-picked) and the images where the fine-tuned model finds the smallest share of ground truth.
  `iou` is intersection-over-union of two boxes; `recall_at_iou` counts a ground-truth box as found only if a same-class prediction
  overlaps it with IoU ≥ 0.5, and each prediction can explain at most one ground-truth box (greedy best-first matching).
  `index.json` stores seed, thresholds and per-image statistics.
- **`scripts/record_environment.py`** — writes Python / torch / ultralytics / CUDA versions to `results/environment_<tag>.json`, because `requirements-train.txt` only gives version ranges.

### Tests
- **`tests/test_pipeline.py`** — builds a tiny fake VOC dataset (with deliberate defects: out-of-bounds box, zero-width box, unknown class,
  aspect-ratio mismatch) and checks the whole inspect → convert → validate → EDA path. It also pins the AP-indexing fix and the IoU/recall helpers.
  The fake data tests the *code*, not IDD itself. Run: `python -m pytest -q tests` (14 pass).

## 4. Design decisions and the reason for each

| Decision | Reason |
|---|---|
| Inspect real files before converting | formats differ from documentation; assumptions silently corrupt labels |
| Never raise on a bad annotation; log it with a code | one broken file must not stop a 41k-image conversion, and the log shows exactly what was dropped |
| Validate the *output* of the conversion | proves the dataset is usable, independent of the converter |
| Resize to 640 px at conversion time | fits Colab/Drive; labels are normalised so they remain valid |
| Same architecture for both models | the only changed variable is the training data, so a difference is attributable to fine-tuning |
| Baseline scored only on direct-match classes | scoring `rider` against COCO `person` would grade the model against the wrong ground truth |
| N/A instead of 0 for India-specific classes in the baseline | a missing label is a vocabulary gap, not a detection failure |
| Compare per group, not one overall mAP | overall mAP mixes real numbers with structural zeros |
| Fixed random seed for the qualitative sample | reproducible and not hand-picked |
| Every number comes from a script that was run | integrity rule in the README; each JSON stores the command that produced it |

## 5. Questions about the code, with answers

**What is the YOLO label format?** One text file per image, one line per object: `class_id x_center y_center width height`, all divided by the image size so they lie in 0-1. That is why resizing an image does not break its labels.

**Why are there two checks on the data (convert and validate)?** Convert guards against bad input; validate checks the files that were actually written. Together they catch converter bugs as well as dataset defects.

**What does `clip_box` do and why?** Some annotated boxes extend past the image border. Clipping to the image keeps them inside the 0-1 range YOLO requires; it is logged as a warning rather than dropping the object.

**Why `except` blocks that do not crash?** A single corrupt XML must not abort the run. The problem is recorded in `conversion_issues.csv` with a reason code, so nothing disappears silently.

**What is IoU?** Area of overlap divided by area of union of two boxes (0 = no overlap, 1 = identical). Detection is counted as correct when IoU passes a threshold; mAP50 uses 0.5, mAP50-95 averages thresholds 0.5, 0.55, … 0.95.

**What is AP / mAP?** AP is the area under the precision-recall curve for one class; mAP is the mean over classes. Precision = correct detections / all detections; recall = correct detections / all real objects.

**Why `conf=0.001` in `evaluate.py`?** AP is computed by sweeping the confidence threshold, so the model must keep even very low-confidence boxes. A high threshold would cut the curve short and lower AP artificially. (The display threshold in the galleries is 0.25 because pictures would otherwise be unreadable.)

**What does `--coco-baseline` change?** It translates ground-truth class ids into COCO ids and keeps only direct matches, so a COCO model can be scored at all. Without it the model's class ids (0 = person, 2 = car, …) would be compared with IDD ids (0 = person, 1 = rider, 2 = car, …) and the scores would be meaningless.

**Why is `train` 0.000 for both models?** Only 13 val boxes of that class exist, so no conclusion can be drawn. It is reported, not hidden.

**Why are precision and recall 1.0 / 0.0 for `caravan`?** At the F1-optimal threshold there are no detections, so precision is vacuously 1.0 while recall is 0. It is an artefact of having 11 val boxes.

**What would you do with more time?** Finish the remaining 7 epochs (expected gain ≈ +0.003 mAP50-95), run several seeds to measure variance, try a larger YOLO model, and evaluate on a held-out dataset (the public release has no test labels, so the current numbers are slightly optimistic because the best checkpoint was chosen on the same val split).

**How do you reproduce the results?** `docs/results_report.md` §11 lists the exact commands; each `results/eval_*.json` also stores the command that produced it.

## 6. Quick commands

```bash
python -m pytest -q tests                                   # self-test
python scripts/prepare_dataset.py                           # convert + validate
python scripts/analyze_dataset.py                           # EDA figures
python scripts/train_yolo.py --dry-run                      # check training setup
python scripts/evaluate.py --model models/best.pt --tag finetuned
python scripts/evaluate.py --model yolo11n.pt --tag coco_baseline --coco-baseline
python scripts/compare_evals.py
python scripts/qualitative.py --finetuned models/best.pt --baseline yolo11n.pt
python scripts/record_environment.py --tag local
```
